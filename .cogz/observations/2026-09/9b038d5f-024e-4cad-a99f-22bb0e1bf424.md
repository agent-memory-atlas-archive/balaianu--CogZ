The stale-installed-binary trap hit two new surfaces in this campaign, on top of run6's original finding — this is a recurring failure mode, not a one-off:

1. **Replay harness**: worktree agents resolved `cogz` via ambient PATH to a stale `~/.local/bin` install (schema v6 vs v7 worktree DB). `entities_accessed=0` — the agent hit SchemaVersionMismatch and correctly abandoned the tool, silently zeroing measured adoption. Fixed by prepending the binary-under-test's directory to the agent subprocess PATH.
2. **Devin's own MCP config** (`~/.config/devin/mcp_config.json`): pointed at the same stale `~/.local/bin/cogz` — every tool call on the v7 repo DB failed on connect. Fixed by pointing at `target/release/cogz`. Both surfaces were running `ensure_schema_version`'s hard-fail on any mismatch — the failure is loud at the API layer but invisible to orchestration that just sees zero uptake.

**Pattern**: any eval/integratation harness that doesn't resolve cogz to the exact binary under test silently measures the wrong system. Check `target/release/cogz` vs every PATH-resolved install whenever a schema version bumps — and treat 'agent didn't use the tool' as a diagnosis requiring the transcript, not a result.
