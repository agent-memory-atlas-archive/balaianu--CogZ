During the end-to-end MCP dogfooding session, search with real ONNX models over the MCP transport initially appeared to hang (30s timeout in the Python test script). Investigation revealed this was NOT a bug — it was the first ONNX runtime load taking ~40s. Once loaded, the model session is cached and subsequent calls are fast (<2s). The MCP server is a persistent process, so this is a one-time startup cost. The subprocess tests use a fake HOME to force FTS-only mode, which is why they complete in ~12s. This is the intended design: foreground index returns quickly, background embedding continues async, and the MCP server loads models lazily on first search call.
