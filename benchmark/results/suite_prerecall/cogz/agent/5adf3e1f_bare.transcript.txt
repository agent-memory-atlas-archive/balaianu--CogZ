## What was wrong

`sync_code_entities` (the full-index path used by `index_code`) only ran `mark_stale_code_entities`, which marks code entities stale when their entire `file_path` disappears from the scan. Entities for functions/types removed *inside* a still-existing file stayed `active` with stale content — still retrievable by search. The incremental path (`sync_code_entities_incremental`) already handled this via `mark_stale_for_removed_entities`.

## Change

In `src/index/sync/mod.rs`, `sync_code_entities` now runs the same per-file sweep after the file-level pass:

```rust
result.marked_stale = mark_stale_code_entities(&conn, &file_to_entity_ids, failed_paths);

let (removed_count, removed_ids) = mark_stale_for_removed_entities(&conn, &file_to_entity_ids);
result.marked_stale += removed_count;
result.removed_entity_ids = removed_ids;
```

Removed ids flow into `removed_entity_ids` for knowledge flagging (in the no-git fallback, `reindex_code`'s `query_stale_code_ids` picks them up since it selects all stale code entities). Files that failed to read are untouched — they aren't keys in `file_to_entity_ids`, so the per-file sweep can't see them. Also updated the function's doc comment to reflect both stale-marking behaviors.
