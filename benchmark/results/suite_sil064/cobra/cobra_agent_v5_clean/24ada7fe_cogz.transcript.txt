## Changes

**`completions.go`** — `InitDefaultCompletionCmd` now takes `args ...string`. When the command has no real subcommands, the `completion` command is only added if it's being invoked (`args[0] == "completion"`) or being completed (`args[0]` is `__complete`/`__completeNoDesc` and `args[1] == "completion"` with more args after it — i.e. `completion` is a fully-typed word, not the `toComplete` word itself). The hidden `__complete` command, already added by `initCompleteCmd`, is excluded from the subcommand count.

**`command.go`** — in `ExecuteC`, `InitDefaultCompletionCmd(args...)` now runs *after* `initCompleteCmd(args)`, which required computing `args` earlier. `InitDefaultHelpCmd` stays before `initCompleteCmd` — otherwise a lone `__complete` would count as a subcommand and trigger adding `help` to root-only programs (would break `TestValidArgsFuncSingleCmd`, which expects no `help` suggestion). `checkCommandGroups` still runs after all commands are created so the completion command's `GroupID` is validated.

Notable edge cases handled:
- `prog __complete completion` (completing the name itself) does *not* create the command — requires `len(args) > 2`, matching `TestCompleteCompletion`'s `:0` expectation.
- `prog completion` on a root-only program works — the cmd is created on demand and shows its help.
- Signature stays backward compatible for direct callers (`InitDefaultCompletionCmd()` still compiles).
